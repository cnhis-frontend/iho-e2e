---
name: iho-test-bootstrap
description: Initialize or repair non-browser behavior testing in Vue 3 IHO projects, including missing dependencies, Vitest configuration, DOM/MSW setup and test typechecking. Use for test infrastructure onboarding or migration.
---

Initialize the base toolchain and validate the application's test host. Add a business flow when the user requests business coverage or supplies a concrete scenario. Report these three results separately. Project installations include a portable toolkit snapshot in this skill's `toolkit/`; commit both IHO skill directories together.

1. Read repository instructions and inspect the working tree, Node version, package manager, lockfile, Vue/Vite versions and existing tests. Preserve existing configuration and user edits. This toolkit targets Vue 3; report other stacks rather than migrating them implicitly.
2. From this skill's directory, run `node scripts/run.mjs init --project <absolute-project-path>` to review the plan. `--apply` installs missing dependencies with the detected package manager, creates configuration/setup/typechecking and runs environment validation. Use `--no-install` or `--no-verify` only when explicitly needed, and report those steps as incomplete. Existing custom files are preserved, not overwritten.
3. Read the project's `iho-test.config.json` and use `node scripts/run.mjs rules --project <path> --id iho.behavior-testing` to obtain pinned public rules. Knowledge is pluggable; honor the project's current provider and the user's permissions. Bootstrap never enables OpenViking or changes plugin configuration.
4. Reuse existing configuration and support. Map actual script names, test configuration, flow directory and documentation in the profile. For every initialization, run `node scripts/run.mjs info` and read its `adaptationGuide` absolute path, especially Application host acceptance. Apply the retrieved rule's initialization and lifecycle requirements to representative real modules; keep adapters and contract tests in the consuming repository.
5. Map the dedicated host contract command as `scripts.host` in the profile. Run `node scripts/run.mjs doctor --project <path> --host` to verify host contracts and test types without requiring business cases. Record the real module imports, providers and external ports exercised. If host validation is incomplete, report base-toolchain success and the specific host gap rather than overall readiness.
6. When business coverage is in scope, implement a flow from an independent requirement/ADR through real DOM interactions and the real service chain, including a relevant failure branch and evidence of bug sensitivity. Run `node scripts/run.mjs doctor --project <path> --run` for configured host, business and type checks. Fix new failures and preserve unrelated existing failures in the report. Generated tests remain runnable without this toolkit checkout.
7. Remove temporary probes, demo components, debug statements and verification-only helpers introduced by this work after their checks pass. CLI starter probes are temporary and are cleaned automatically unless modified; inspect reported retained files and unresolved failed probes before removing them. Keep reusable setup/adapters and real regression coverage. Repair imports, scripts, config and documentation references, then rerun affected real checks. Report cleanup and any retained verification code's ongoing purpose; never add dummy tests to make an empty business suite pass.

Record the actual rule source/version, real and simulated interfaces, test commands/results and remaining limitations in project test documentation. Add a short repository instruction pointing to that document once it exists. Replace old tests only after mapping their business rules to verified coverage.
